# Сервис учета отпусков

## Назначение
Проект автоматизирует процесс планирования и учёта отпусков внутри компании. Позволяет сотрудникам подавать заявки на отпуск, руководителям — согласовывать их, а HR‑отделу — вести единый календарь отпусков и следить за остатками дней.

## Целевая аудитория
Продукт рассчитан на организации, заинтересованные в автоматизации учёта отпусков:
Малый и средний бизнес — компании без выделенного HR‑отдела, которым нужен простой инструмент учёта отпусков.
Крупные компании и корпорации — организации с многочисленным персоналом и развитой кадровой службой.
HR‑отделы / HR‑директора — команды, отвечающие за планирование, учёт и контроль кадровых ресурсов.
IT‑департаменты компаний — как заказчики внедрения и администрирования решения.
Аутсорсинговые HR‑агентства и кадровые сервисы — компании, ведущие учёт отпусков для нескольких клиентов.

## Предметная область
Предметная область — кадровый учёт и управление персоналом. Система хранит типы отпусков и заявки сотрудников на отпуск: ежегодный оплачиваемый, неоплачиваемый, по уходу за ребёнком и по болезни. Для заявок на ежегодный оплачиваемый отпуск учитывается остаток дней; остальные типы его не уменьшают. Система также проверяет пересечение дат, позволяет отменять заявки и восстанавливает баланс дней при отмене оплачиваемого отпуска.

## Основные сущности

### User — пользователь системы

Объект `User` представляет сотрудника, для которого ведётся учёт отпусков.

**Атрибуты:**
- `id` — уникальный идентификатор пользователя;
- `name` — ФИО сотрудника;
- `vacation_days_available` — количество доступных дней отпуска;
- `vacation_days_total` — общее количество дней отпуска за год.

**Методы:**
- `reduce_days(duration)` — списать дни отпуска; возвращает `False`,
  если дней недостаточно;
- `restore_days(duration)` — вернуть дни при отмене заявки;
- `from_data(data)` — `@classmethod`, создать объект `User` из данных JSON;
- `to_dict()` — преобразовать объект в словарь для сохранения в JSON;
- `__str__()` — строковое представление пользователя.

### Vacation — тип отпуска

Объект `Vacation` описывает категорию отпуска.

**Атрибуты:**
- `id` — идентификатор типа;
- `name` — название типа;
- `deducts_vacation_days` — признак, что заявка этого типа расходует доступные дни оплачиваемого отпуска.

В справочнике заданы ежегодный оплачиваемый, неоплачиваемый отпуск, отпуск по уходу за ребёнком и отпуск по болезни.

### VacationRequest — заявка на отпуск

Объект `VacationRequest` представляет заявку на отпуск, поданную пользователем.

**Атрибуты:**
- `id` — уникальный идентификатор заявки;
- `user` — объект `User`, которому принадлежит заявка;
- `vacation` — объект `Vacation`, задающий тип отпуска;
- `start_date` — дата начала отпуска (`YYYY-MM-DD`);
- `end_date` — дата окончания отпуска (`YYYY-MM-DD`);
- `duration` — длительность отпуска в днях;
- `status` — состояние заявки: `pending`, `approved`, `cancelled`.

**Методы:**
- `cancel()` — отменить заявку и вернуть дни пользователю через
  `user.restore_days()`, если тип отпуска расходует баланс;
- `from_data(data, users)` — `@classmethod`, создать объект `VacationRequest`
  из JSON и восстановить связи с `User` и типом отпуска;
- `to_dict()` — преобразовать объект в словарь для сохранения в JSON;
- `__str__()` — строковое представление заявки.

## Веб-интерфейс (ПР5–ПР7)

Веб-интерфейс использует Django-шаблоны и SQL-запросы к SQLite. JSON-хранилище
и консольная версия сохранены; `db/import_json.py` переносит исходные записи в
реляционную базу. Django ORM в ПР7 не используется: представления получают
результаты SQL через стандартный модуль Python `sqlite3`.

| URL | Страница |
| --- | --- |
| `/` | Главная страница и навигация |
| `/employees/` | Постраничный список сотрудников и доступных дней (`LIMIT`/`OFFSET`) |
| `/employees/<int:employee_id>/` | Карточка сотрудника |
| `/employees/available/?date=YYYY-MM-DD` | Поиск сотрудников без активных заявок на выбранную дату |
| `/vacations/` | Справочник типов отпуска |
| `/requests/` | Список заявок с фильтром по статусу |
| `/requests/active/` | Только ожидающие и согласованные заявки |
| `/requests/<int:request_id>/` | Карточка заявки |
| `/requests/statistics/` | Сводка и группировка заявок по сотрудникам и типам |

Страницы используют Django Template Language: общий `templates/base.html`,
наследование через `{% extends %}` и `{% block %}`, подключаемые фрагменты
через `{% include %}`, циклы, условия и фильтры `length` и `default`.
Ссылки формируются именованными URL с пространствами имён, например
`{% url 'leave_requests:detail' vacation_request.id %}`. Общая навигация
находится в `templates/includes/navigation.html`.

Общий шаблон подключает Bootstrap 5.3.3 через CDN и собственную статику
`homepage/static/homepage/`: CSS, логотип SVG и JavaScript. Неизвестный URL
или идентификатор возвращает страницу 404 с HTTP-статусом `404`.

Веб-интерфейс доступен только для просмотра. Создание и изменение объектов
через формы, авторизация и переход на Django ORM относятся к следующим
практическим работам.

## База данных SQLite (ПР7)

Файл базы данных: `data/vacation_accounting.sqlite`. Структура определяется в
`sql/schema.sql`:

- `employees`: `id INTEGER PRIMARY KEY`, `name TEXT`, доступный и общий лимит
  оплачиваемых дней (`INTEGER`, значения от 0 до 28, доступный лимит не больше
  общего);
- `vacation_types`: `id INTEGER PRIMARY KEY`, `name TEXT`, признак списания
  лимита (`INTEGER`, 0 или 1);
- `leave_requests`: `id INTEGER PRIMARY KEY`, ссылки `employee_id` и
  `vacation_type_id` (`FOREIGN KEY`), даты (`TEXT` в формате `YYYY-MM-DD`),
  длительность (`INTEGER`) и статус (`TEXT`).

Ограничения `CHECK`, `NOT NULL`, первичные и внешние ключи проверяют корректность
основных данных. В `db/database.py` настроены `sqlite3.Row` и
`PRAGMA foreign_keys = ON`.

Чтобы создать схему и перенести актуальные исходные JSON-данные, из корня
проекта выполните:

```powershell
python -m db.create_db
python -m db.import_json
```

Скрипт создания использует `CREATE TABLE IF NOT EXISTS`, а повторный импорт
вставляет или обновляет записи по их ID (но не удаляет записи, отсутствующие
в исходных JSON). Сначала импортируются сотрудники и типы отпуска, затем
заявки, поскольку последние ссылаются на первые таблицы. Для старых заявок
без `vacation_id` используется тип ежегодного оплачиваемого отпуска, как и в
существующем JSON-хранилище. Повторный импорт может перезаписать значения
записей с теми же ID в SQLite данными из JSON.

В `sql/queries.sql` сохранены 16 запросов предметной области: списки,
фильтрация, соединение таблиц, поиск сотрудников по дате, агрегирование,
`GROUP BY` и `HAVING`. Представления используют параметризованные запросы
(`?`), а значения результатов доступны шаблонам по именам столбцов.

## Запуск

Установить зависимости в виртуальное окружение:

```powershell
python -m venv venv
venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Создать схему SQLite и импортировать исходные данные (для уже созданной базы
эти команды можно повторно выполнить при необходимости синхронизации), затем
применить служебные миграции Django, проверить конфигурацию и запустить
веб-приложение:

```text
python -m db.create_db
python -m db.import_json
python manage.py migrate
python manage.py check
python manage.py runserver --insecure
```

Открыть `http://127.0.0.1:8000/`. Ключ `--insecure` нужен только для
раздачи статических файлов встроенным сервером при `DEBUG=False`; используйте
его только при локальной разработке. Локальные хосты `localhost` и
`127.0.0.1` разрешены.

Консольная версия предыдущей практической работы сохранена:

```text
python main.py
```
